Purpose

Shows the internal shape of one CMS adapter family. Each operation (cards, balances, transactions, accounts) is a small class inheriting from Paymentology::Base; HTTP and audit-log responsibility is delegated to HttpClients::Paymentology. The same shape is repeated in Postilion::* and Ebc::*.

Decisions & Notes

  • Mirror structure across CMSs. Postilion and EBC use the same Base / Subclass / HttpClient / Log shape so callers can swap implementations transparently.
  • Audit on every call. The HttpClients layer writes a log row for every request; this is non-negotiable and must not be skipped for "ephemeral" calls.
  • Retry is opt-in. Only services that explicitly need it (e.g. UpdateWithRetry) wrap retry; everyone else bubbles errors so callers / Sidekiq retry policy decide.
  • Config via Rails.configuration.x. Base URI and credentials come from X_PTL_CONFIGS / application.yml, not hard-coded.

Assumptions

  • Method signatures shown (get, post) are illustrative; the real client may expose request(verb, path, …).
  • Per-CMS log tables in the codebase are paymentology_log / postilion_log / ebc_log; the model class names follow the same convention.
