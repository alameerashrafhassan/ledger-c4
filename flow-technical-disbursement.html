Disbursement — Technical sequence

What actually runs when an approved disbursement is processed: HTTP entry through DisbursementsController, async hand-off to Disbursements::Processor, ledger writes through Ledger::CreateTransaction, fan-out per employee via SubProcessor, and side-effects (mailers, SMS jobs, Segment).

Events / side-effects emitted

  • DisburserMailer.new(disbursement).call — sends email summary at finalise.
  • Notifications::Disbursements::Success — internal notification at finalise.
  • Analytics::SegmentPublisherJob — fired only on completed (with cumulative metrics).
  • SmsSenderJob — per-employee on successful pay step.
  • UnlinkEarnedWagesJob — only on failed cycles, to detach EWA from this disbursement.

Concurrency concerns

  • Double-processing: prevented by disbursement.with_lock + in_progress? guard. A second worker that picks up the same id either blocks then raises, or sees in_progress and raises immediately.
  • Two Ledger writes from concurrent flows on the same account: each call goes through its own DB transaction; UpdateLocalAccount writes accounts.posted_balance_cents; concurrent updates serialise on the row lock acquired during the UPDATE. There is no application-level optimistic version field.
  • Sidekiq retry storms: a transient DB error on the load step can cause a retry. Idempotency relies on trx_uuid uniqueness and on the disbursement state machine — replays of an already-completed disbursement raise UNIQUENESS_ERROR on the lock check.

Failure handling

  • Validation failure inside Ledger::CreateTransaction → row flipped to status: :failure, errors persisted on the LedgerTransaction; no entries posted.
  • Per-employee failure → employee_disbursement.status = :failed, processor continues. The cycle finalises as :failed if any employee failed.
  • Failed cycle triggers UnlinkEarnedWagesJob; reversal of any successful employee payments is operator-driven through the Reversal flow (Ledger::RevertTransaction).

Observability

  • Standard Rails request logs at the controller layer.
  • Sidekiq job logs with jid and disbursement_id.
  • processor_activity_log entries for CMS-bound calls (per CMS log table — paymentology_log / postilion_log / ebc_log).
  • LedgerTransaction.transaction_errors column captures validation failures.
  • Segment events at finalise for analytics.
