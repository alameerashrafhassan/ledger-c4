Reversal — Technical sequence

No HTTP endpoint for reversal was found in the controllers; the path is operator-driven via console or another service that wraps it. Internally: Ledger::RevertTransaction wraps Ledger::CreateTransaction with the original entries' accounts swapped, then links the original to the new transaction.

def call
  return false unless creator.call

  transaction.update reversal_transaction: creator.transaction
end

def from_account
  ledger_entries.credit.first!.account
end

def to_account
  ledger_entries.debit.first!.account
end

def amount
  ledger_entries.first.amount
end

Note: amount is taken from ledger_entries.first; entries always come in matching pairs (debit + credit, equal amount), so any one is the reference.

Events

No events emitted by this service. Downstream consumers should react to LedgerTransaction creation rather than to a "reversed" signal.

Concurrency concerns

  • Double reversal: nothing in the service blocks reverting the same original twice. Callers (operators) are responsible for checking original.reversal_transaction_id.nil? before calling.
  • Concurrent writes to the involved accounts: serialise on accounts row locks during balance UPDATE.

Failure handling

  • Constructor guard prevents reversal of non-posted transactions.
  • Inner CreateTransaction failure surfaces through creator.errors exposed by RevertTransaction#errors.
  • Link UPDATE failure leaves a posted reversal without a back-reference; needs manual repair.

Observability

  • Standard ActiveRecord SQL logs.
  • Two new LedgerTransaction rows per reversal event are the audit trail (original + reversal, linked via FK).
