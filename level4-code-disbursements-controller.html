Purpose

Shows the disbursement multi-step workflow at the code level: how the controller delegates to per-action service objects, transitions the model state machine, and enqueues a Sidekiq job for the heavy CMS-bound work.

Decisions & Notes

  • Service-per-action. Workflow steps are explicit objects (Submit, Approve), not boolean flags on a single God service — easier to test and audit.
  • Heavy execution is async. Approval enqueues a job; the API doesn't block on CMS-bound work.
  • State machine is in the model. Transitions are validated centrally on Disbursement, not by ad-hoc controller checks.

Assumptions

  • Action names shown are illustrative; the codebase may include extra actions (e.g., resubmit, retry).
  • Service object names follow the canonical "Disbursements::ActionName" convention used elsewhere in app/services/disbursements/.
