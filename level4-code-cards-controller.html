Purpose

Shows how the Cards controller wires the HTTP route to the Card model, the CardPolicy, and the CMS-bound service classes via ProcessorMediator. The same shape applies to other resource controllers; this is the canonical example.

Decisions & Notes

  • Controller never picks a CMS. It always asks ProcessorMediator with the card's beneficiary.
  • Pundit policies live alongside the resource. Adding a new action requires adding a corresponding policy method.
  • EBC card detail goes via CDE. The Ebc::Cards::Details service goes through the CDE proxy — no other path exists.

Assumptions

  • Action set shown reflects common card endpoints; the actual controller may include card-operation specifics that live under card_operations/.
  • The beneficiary_for(card) helper is illustrative and may live in a concern.
