C4 Level 3 — Components inside ProcessorMediator + CMS Adapters

The CMS abstraction layer: a single dispatcher and three sets of adapter services, plus shared HTTP/log infrastructure.
Component External System Cylinder = data store

Purpose

Inside the CMS-mediation container, this view shows the dispatcher (ProcessorMediator), the three CMS adapter families, and the HTTP-client/log layer that backs them. The diagram exists primarily to make the "single choke-point" rule visible.

Decisions & Notes

  • Same-shape services across CMSs. Adapters for the same service_key share initializer signature, so callers can swap implementations transparently.
  • Per-CMS log table. Each HttpClient writes to its own log table; this preserves provider-specific schemas and avoids one giant logs table.
  • EBC via CDE only. The HttpClients layer encodes this constraint — no adapter is allowed to bypass it.
  • EBC mapping is partial. Several entries in ProcessorMediator::MAPPING still point at Ebc::Base as a TODO placeholder.

Assumptions

  • Common Services is shown as a single block; in practice it's a small folder (app/services/common/) — promote individual classes if they grow.
  • Treasury DB writes from this container are limited to fund-flow / suspense operations; treasury CRUD generally goes through Treasury Controllers.
