C4 Level 4 — Code: ProcessorMediator

Class diagram of the dispatcher itself, its MAPPING table, and how it picks an adapter from a beneficiary's cms_marker.

Purpose

Shows what's actually inside app/services/processor_mediator.rb: a static MAPPING table from a service_key (e.g. :show_card) to a hash keyed by cms_marker. .for(key, beneficiary) picks the right class and instantiates it with the beneficiary.

Decisions & Notes

  • Static mapping, not dynamic registration. Adapter wiring lives in one Ruby hash so it's grep-able and reviewable in a PR; new CMS additions need an explicit edit.
  • Same initializer signature per service_key. Adapters for the same key must accept the same args so the call site stays uniform.
  • EBC entries that point at Ebc::Base are explicit TODO placeholders — they will raise/no-op until the EBC implementation lands.
  • Two balance update keys. protected_update_balance and update_balance are intentionally separate so tests don't always pay retry overhead.

Assumptions

  • Service-key naming is a soft convention (snake_case verbs); the canonical list is the MAPPING constant.
  • Future expansion (new CMS) is expected to add a fourth column to MAPPING rather than introduce a sibling registry.
