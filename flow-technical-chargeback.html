Chargeback — Technical sequence

Settlement runs synchronously inside the controller (no Sidekiq hop). The flow is: ChargebacksController → Chargebacks::Settle → Ledger::CreateTransaction; an SMS notification job is enqueued only after the ledger commit succeeds.

Events / side-effects

  • Chargebacks::SmsSenderJob.perform_later(chargeback.id) — only on success.
  • No external event bus emission found in the chargeback path.

Concurrency concerns

  • Double-approval: two operators clicking simultaneously — second blocked at with_lock, then sees non-pending and is rejected.
  • Suspense balance contention: many chargebacks settling in parallel all touch the suspense row. Updates serialise on accounts row locks during UpdateLocalAccount.

Failure handling

  • Lock-stage failure: rescue in call attaches :invalid_chargeback_approval; no DB writes.
  • Ledger validation failure: chargeback.status set to failed; LedgerTransaction.status = failure.
  • Erroneous-but-posted approval: reverse via Reversal.

Observability

  • Standard Rails request logs and Sidekiq worker logs (for the SMS job).
  • Per-CMS log table entries from any downstream CMS balance update.
  • chargebacks.status + ledger_transactions.transaction_errors are the canonical post-mortem signals.
