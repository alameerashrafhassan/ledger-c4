C4 Level 2 — Containers inside PayEngine 2.0

Runtime processes and data stores that make up the PayEngine system, and how they collaborate with external systems.
Container (PayEngine) External System Cylinder shape = data store Dashed border = system boundary

Purpose

This level zooms inside PayEngine 2.0 to show the deployable / runtime containers — the Rails API, the Sidekiq worker fleet, the in-process CMS-mediation layer, plus the data stores. It's the right level for a new engineer onboarding or for capacity / deploy discussions.

Decisions & Notes

  • API and Workers share the same codebase. They differ only in process boot (Puma vs Sidekiq), so domain code is shared and the CMS adapters are the same Ruby classes.
  • Treasury DB is a second physical database. Treasury models inherit from Treasury::BaseRecord with its own connection; this is a hard architectural boundary to preserve.
  • ProcessorMediator is in-process, not a separate service — drawn as its own container to highlight that it's the single point of CMS routing.
  • EBC traffic must traverse CDE. No adapter is allowed to talk to EBC directly.

Assumptions

  • Single Redis instance per environment serves both Sidekiq and cache. If split, this needs to become two cylinders.
  • Per CLAUDE.md, the Rails API is API-only; if a back-office UI is later added, it would become a new container.
